# Канцлер Про — доработки и расширение функционала (Backlog)

Документ описывает **возможные улучшения программы и расширения функционала**.
Составлен по итогам аудита кода (ноябрь 2026) и отражает текущее состояние репозитория.

Статус на момент написания: ✅ 43 теста зелёные, `ruff check .` чистый, CI (lint + compileall + pytest + pip-audit) настроен.

Легенда приоритета:
- **P1** — критично / высокий эффект при малых затратах;
- **P2** — важно, планово;
- **P3** — желательно, «вишенки».

Оценка трудозатрат: **S** ≤ 1 дня, **M** 1–5 дней, **L** > недели.

## 2. Безопасность

| # | Идея | Приоритет | Трудозатраты | Описание |

| B-1 | Серверная проверка прав при мутациях | P1 | M | RBAC сейчас проверяется на уровне навигации (`authz.require_admin`). Следующий шаг — проверки внутри функций-мутаторов (`add_encouragement`, `update_review`, `delete_user`…): оператор обязан быть администратором либо иметь право на конкретное действие. | B-3 | Проверить миграцию старых хешей паролем | P3 | S | PBKDF2 реализован в `security.py`; убедиться тестами, что старые хеши корректно мигрируют при первом входе. |

## 7. Что НЕ стоит делать сейчас

- **Переписывать UI на другой фреймворк** — Flet 1.0.5 стабилен в проекте, миграция дороже любой выгоды.
- **Внедрять ORM (SQLAlchemy)** ради «правильности»: параметрический SQL + белый список идентификаторов работают, инъекций аудит не нашёл; польза ORM появится только при переходе на клиент-сервер (F-8).
- **Микросервисы / DI-контейнеры / event bus** — для монолита ~10k строк это избыточно.
- **Глобальное разбиение `database.py`** до завершения миграции SQL в репозитории (A-1) — иначе придётся переносить код дважды.
